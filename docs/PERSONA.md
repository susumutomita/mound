# mound ペルソナ — 草野球チーム運営担当

mound の設計・実装・エージェントの挙動は、すべてこのペルソナの **実運用** から導く。
「それっぽい default」を足す前に、必ず「この人は実際どう使うか?」を問う。
判断に迷ったら、機能仕様ではなく **このペルソナの 1 日** を思い出す。

---

## ペルソナ: 「トモ」— 草野球チーム Xeros の代表

- 30〜40 代。平日は本業フルタイム。チーム運営は片手間で、ほぼスマホ片手。
- 草野球歴は長いが、一番の負担は運営の事務(日程調整・連絡・出欠・集金)。
- **自分もプレーしたい。** 運営に時間を取られたくない。

### ゴール
- 運営の手間 (toil) を最小化する。「伝えるだけで動く」。
- 毎月のルーティンを落とさず回す。ドタキャン・ダブルブッキングを避ける。
- **全自動が欲しいわけではない。** 判断と最後の一手は自分でやる。

### コンテキスト
- 本拠地 = 横浜。活動 = 毎週土曜。メンバー 10 人前後。
- **本名を出したくない人がいる** → ニックネーム運用。
- グラウンドは市営の **抽選予約 + キャンセル狙い**。会費は **PayPay 割り勘**。

### 毎月のルーティン (mound が支える対象)
1. グラウンドの **抽選予約を入れる**(市サイトに人手で申込。mound は申込/当落の記録とリマインド)
2. **出欠を取る**
3. **キャンセル監視**(空きが出たら掴む)
4. **人数が揃ったら試合確定** → PayPay 割り勘で **精算**

### メンタルモデル / 当たり前の期待 (★ default はここから導く)
- 「空きグラウンド教えて」= **今より先(実行時点以降)の空き** が見たい。
  過去・2 週間前のキャッシュ・テストデータは論外。「直近 N 時間に取得した分」みたいな
  内部都合のフィルタは **使い方として存在しない**。
- 市の予約サイトを **叩きすぎてブロックされるのは絶対 NG**。取得は間隔を空け、参照はキャッシュから。
- 自動化は手間削減のため。**判断・軽い手動(リンク貼り・入金消し込み)は人がやってよい**。
- 本名・余計な個人情報・使いもしない default はいらない。
- データはチームが所有(SQLite/Turso)。端末やエージェントを変えても続きから動く。

### 地雷 (これをやると信用を失う)
- 実運用と乖離した「それっぽい default」(例: `ground list` の「直近 48h 取得ぶん」)
- 古い / テスト / 過去のゴミを混ぜて出す
- 確認なしで実データを壊す
- 実際は終わっていないのに「完了」と報告する(push/反映していないのに「マージした」)
- 頼んでいないのにスコープを膨らませる / 逆に手を抜く

### 「良い」の定義
言われた業務が、**最小の手間で・現実に即した挙動で・確実に** 回ること。
AI は提案する。最後は人が決める。

## このペルソナから導かれる具体ルール (抜粋)

| 場面 | ペルソナから導く正しい挙動 |
| --- | --- |
| `ground list` の既定 | **実行時点以降の空き** (date_iso >= 今日)。取得時刻ではフィルタしない |
| グラウンド取得 | `ground sync` は cron で **間隔を空けて**。参照 (list/match/diff) はキャッシュ |
| メンバー登録 | `name` は表示名/ハンドル。**本名は不要・前提にしない** |
| 自動化の範囲 | **toil 削減に限定**。外部 API が無い所(PayPay 投入・抽選申込)は人手のまま |
| 破壊的操作 | 実データの削除・外部送信は **人の承認** を取る |
| 「完了」 | **実際にマージ/反映/検証してから** 言う |

迷ったら、機能を増やす前に「トモはこれで楽になるか? 現実に即しているか?」を問う。
